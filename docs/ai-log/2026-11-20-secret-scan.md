# AI ログ: 秘密の混入検査を CI に入れる

- 日付: 2026-11-20
- 関連: ADR-0006、T7 のセキュリティレビュー 5、docs/plan/phase1-plan.md の T8
- 使った AI: Claude(claude-opus-5-5)

## 指示

PR #7 のマージのあと、人間が「GitHub の secret scanning と push protection を AI が gh で有効にする」(推奨)を選んだ。あわせて、本物のキーで通信を始める T8 の前に、CI に gitleaks を入れる。

## 出力

- CI に `secret-scan` のジョブを足した。gitleaks v8.30.1 の公式のコンテナで、リポジトリの全履歴を調べる。見つかった値はログに出さない(`--redact`)
- `.gitleaks.toml`: gitleaks の標準の規則を使い、テストのダミーのキー(PKTESTKEY000…、TestSecret000… など)だけを除外する
- SPEC-006 の決めたこと5(まだ保存していない時の値)を、人間が確認したと書いた(2026-11-20)

## GitHub の secret scanning を有効にできなかったこと

- `gh api -X PATCH` でリポジトリの設定を変えようとしたが、AI の作業環境からはリポジトリの設定の書き込みが許されていなかった(HTTP 403)
- その時に、リポジトリが **非公開(private)** だと分かった。人間に「公開リポジトリは無料」と説明していたが、確かめていなかった。非公開のリポジトリで secret scanning を使うには、有料の機能(GitHub Advanced Security)が要る見込み(確かめていない)
- 人間に伝え、公開する時に有効にするかを決めてもらう

## 版の決め方

- gitleaks の最新の安定版は v8.30.1(2026年3月)と、複数の資料で確かめた。作者は「機能は完成していて、今後は安全上の修正だけ」としている
- gitleaks-action は Node 20 で動く版があり、GitHub の実行環境から Node 20 が外される予定がある。依存を増やさないよう、公式のコンテナを版のタグと中身のハッシュ(digest)で固定して使った。digest は、最初の CI の実行でコンテナを取ってきた時のログ(Digest: sha256:c00b6bd0…)から取った。最初に取ってきた中身を正しいものとして固定する形で、gitleaks の作者が公開している値と見比べてはいない

## 確かめたこと

- AI の作業環境では gitleaks もコンテナも動かせないので、この PR の CI で確かめた
  - 1回目(eff8937、digest の固定の前): 「28 commits scanned」「no leaks found」
  - 2回目(bb8331f、digest で固定): 「29 commits scanned」「no leaks found」。pull した digest は固定した値と同じ
  - 3回目(レビューの修正のあと): 結果は PR に書く
- テストのダミーのキーを除外する正規表現が、リポジトリにあるダミーのキー6種類(src と e2e)に当たることを、grep で一覧を作って見比べた

## レビュー(security-reviewer)と対応

指摘は9件(高 0、中 4、低 5)。人間の指示(2026-11-19)により、AI が推奨どおりに直した。

| 番号 | 重要度 | 指摘(要点) | 対応 |
|---|---|---|---|
| 1 | 中 | checkout が GitHub のトークンを .git/config に残し、外部のコンテナに書き込みもできる形で渡している | `persist-credentials: false` にし、コンテナには読み取り専用で渡す |
| 2 | 中 | ワークフローの権限の指定がない | 最上位に `contents: read` を書いた |
| 3 | 低 | 除外の正規表現が前後を固定しておらず、部分一致になっている | 実在のダミーの形に、前後まで固定した |
| 4 | 中 | Alpaca のキーを見つけられるか確かめていない。DB ファイルがコミットされても中身を見られない | Alpaca のキー ID の規則を足した。管理下に data/、.db、.sqlite、.env、.e2e/ があれば失敗する手順を足した |
| 5 | 中 | 本物の形を見つけられること、値が隠れることを確かめていない | CI で毎回、実行の時に作る偽のキーを一時の場所でコミットし、見つけること(終了コード 1)、ログに値が出ないこと、テストのダミーは除外されること(終了コード 0)を確かめる手順を足した |
| 6 | 低 | digest は最初に取った中身を信じる形。更新が手作業になる | ADR-0006 に追記した。作者の公開している digest と見比べるのは人間に頼む |
| 7 | 低 | 記録の件数が digest の固定の前の実行のもの | 実行ごとに書き分けた |
| 8 | 低 | CI は混入を防がない。push protection は使えない見込み | ADR-0006 に追記した。コミットの前に調べるフックは任意として入れていない |
| 9 | 低 | 秘密の検査と関係のない SPEC-006 の変更が混ざっている | 小さい変更のため分けなかった。人間の確認は、2026-11-20 のチャットでの質問への回答(「このままでよい」)と PR の本文に書いた |

## AI が間違えた点と学び

| 間違えた点 | どう分かったか | 次からどうするか |
|---|---|---|
| 検査を入れただけで、見つけられることを確かめていなかった(漏れ0件は、検査が働いていない時も同じ結果になる) | security-reviewer の指摘 | 「何も見つからない」が結果の検査は、見つかるはずの入力で一度動かして確かめる |
| リポジトリを公開だと思い込み、「公開リポジトリは無料」と人間に説明した | 設定を変える API の応答と、リポジトリの情報を見た時 | 料金や条件に関わる説明の前に、リポジトリの公開・非公開などの前提を確かめる |

## 確かめていないこと

- Alpaca のキー ID が本当に「PK か AK で始まる20文字」か(一般的な形として書いた。人間が自分のキーの文字数と先頭2文字を見て確かめる)
- シークレットだけが漏れた時に見つけられるか(標準の汎用の規則に頼っている)
- digest が gitleaks の作者の公開している値と同じか
